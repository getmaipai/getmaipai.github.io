The context layer

robot/context/ keeps a handful of facts fresh so a conversation starts with the robot already in the same day the family is in. The hard part is not gathering data. It is refusing almost all of it.

The budget decides the design

The robot thinks with a 1 to 3B model on the Pi. cognition/dialogue/prompt.py already trims history to 800 characters because a small model does worse when crowded, and the ambient block gets 700 characters, total, forever. That is six to eight facts. Every fact added evicts one already there.

So a fact has three possible destinations, and conflating them is the mistake this layer exists to avoid:

DestinationCostExample
In the blockTokens on every turn, foreverThe weather line, an active warning
In the cacheOne poll, no prompt costDew point, the moon, an AQI of 35
On askNothing until usedTomorrow’s forecast

Render the unusual, not the inventory

A block that prints front door locked every turn spends its budget on something true 98% of the time, which carries almost no information. Fact therefore has two flags: always for the handful worth a slot regardless (the weather line), and abnormal for everything else, which renders only when it is out of the ordinary. On a quiet evening the block is four lines; during a storm it is eight. That is how 250 candidate facts fit in 700 characters.

Standalone first, three tiers plus a seam

TierNeedsCovers
ComputedNothingSun and moon, holidays, seasons, bin day, birthdays, time-until
SensedThe robot’s own busRoom, presence, climate, battery, tasks, media, health
FetchedThe robot’s own internetWeather, severe alerts, air quality, one optional headline feed
SeamAn optional provider, absent by defaultCalendar, household sensors, media libraries

ContextProvider copies the shape HardwareBundle already uses: everything optional, whatever answers gets attached, and an absent provider is reported as honestly missing rather than faked. A hub is one implementation of that seam and deliberately not the only one, so nothing in robot/context/ may import hublink. A household with no calendar provider gets no calendar line, and the robot says the calendar is not connected if asked.

Publishing only on a material change

ContextState is published when the facts change, never on the poll timer. The system prompt prefix has to stay byte-identical between turns for the model’s KV cache to be reused, and that matters most on the machine with the least to spare. facts.signature() fingerprints the fact set ignoring timestamps, so a poll that returns the same weather it returned fifteen minutes ago is silent. This is Home Assistant’s always_update=False, for the same reason.

Manners, and why they are structural

None of these services needs a key, which means none of them can throttle us politely: the first sign of asking too much would be the household’s address being blocked. So limiter.py is a single choke point, and feeds are handed a LimitedWebTool rather than the raw one. There is no unlimited handle for a later feed to find.

  • A token bucket per host, because the host is what does the banning. One request per second, the strictest published limit among the services we use, applied to all of them.
  • A daily budget per host, which catches the failure a rate limit never sees: a bug polling every tick stays under one request per second forever while quietly making tens of thousands of calls a day.
  • Quiet mode after repeated refusals. Never retry through a block.
  • Staggered and jittered cadences, so the robot never opens three connections at once and two robots never fall into lockstep.
  • Cadence matched to the source. Home Assistant makes this an integration-quality rule and the reasoning holds: polling faster than the upstream refreshes is pure waste, and waste is what gets an address blocked.

Shipped cadences use roughly 430 calls a day across all three feeds, well inside Open-Meteo’s free non-commercial allowance. The gap between that and the daily cap is deliberate: it is the room a bug has to be caught in before a service notices.

The web tool sends an honest user agent naming the software. api.weather.gov asks callers to identify themselves, and a service that can see who is asking can ask us to slow down instead of blocking the house.

The capability catalogue

registry.py maps a capability (weather.current, alerts.weather) to a primary source, ordered fallbacks, a refresh interval, a TTL and a confidence. Skills ask for the capability and never learn which service answered, so a source can be replaced, failed over, or swapped for a local copy without touching a skill.

Three rules keep the catalogue honest:

  • Every entry carries a status in the repo’s own vocabulary. live means implemented and tested; planned means the source is vetted and the entry is a design note. A planned row never implies a capability the robot has.

  • TTL is always a multiple of the refresh, so one missed poll is invisible and a dead source goes quiet instead of quoting old numbers as current.

  • Every source declares how it is reached, which is a different question from how much to trust it and a more important one: open, rate-limited, unofficial, or login-required. This is a gate, not a label, and check_access_policy() is asserted in the test suite (see below).

SourceChain runs primary then fallbacks until one answers. Failover is not sticky: a fallback answering does not promote it, because the primary is primary for a reason. A declared but unimplemented source is skipped, never faked.

Who may interrupt

Exactly one thing: a National Weather Service alert at severity Severe or Extreme. It is published as a ProactiveCandidate with verbatim=True, so the brain’s existing gate still decides whether the robot actually speaks, and quiet hours, presence and the care layer all still apply. It is offered once per alert, not once per tick.

The privilege is narrow on purpose. A robot that announces every frost advisory is a robot a family mutes, and a muted robot cannot warn anybody about anything.

What the robot deliberately does not do

There is a large, tempting toolbox for getting data without an API key: yt-dlp, gallery-dl, Instaloader, ytmusicapi, Streamlink, and library search wrappers that scrape a search engine’s results page. All of them run fine on a Pi, none of them needs a daemon, and every one of them is a reverse-engineered client.

Two hard lines are enforced in code by check_access_policy():

  • An unofficial source may never be a primary. It can be a fallback. If the only way to get something is to pretend to be a browser, the honest answers are to ask less, to sign in through a front door that actually exists, or to drop the feature.
  • A login-required source may never be used ambiently at all. An account carries an identity, and an identity is exactly what this layer promises never to send. Anything needing one belongs behind an explicit per-household connection, not a background poll.

The reason is not squeamishness. On 2026-08-28 the hub’s home address was walled by a video platform for a day because background traffic far exceeded what a person could produce, and every family member’s player went dark. The robot is the device in the house that most needs to keep working, and it shares that address. That another device already doing something is never an argument against the robot doing it locally (owner’s rule, 2026-09-02: the robot is standalone first, so duplicating a capability on-board is the point); the argument is about pace. Any media capability the robot grows carries its own limiter and daily budget through this layer’s single choke point, exactly like the feeds above, so two well-behaved clients never add up to one scraper.

Search-scrape-summarize gets the same answer for a second reason. A 1 to 3B model summarising a scraped page, spoken aloud as fact to a household that includes children, is a confabulation engine, and prompt.py already promises the opposite: never state a recent event as certain, offer to check instead.

What is worth taking from that toolbox is the structured data sites already publish for machines. A shop’s page carrying schema.org OpeningHoursSpecification is publishing it to be read, and reading it is one request to one page somebody asked about. That is the front door. It is in the catalogue as nearby.hours, still planned, and it will be cached hard and always spoken with its provenance and its age.

Not a daemon in sight

Nothing in this layer runs a service. No database, no container, no browser, no search server, no message queue beyond the bus the robot already has. The computed half is arithmetic on a timer, the feeds are HTTP requests on a schedule, and the calendar is a file read when its mtime changes. Idle cost is one coroutine ticking every thirty seconds, which matters on a machine that is also running a wake word, speech recognition, speech synthesis and a language model.

Ageing out, everywhere

A TTL that only filters at render time hides a stale fact without letting it go, which on a machine that stays up for months is how memory creeps. So every cache in this layer sweeps itself, and none of them needs a timer or a background task:

WhereWhat is droppedWhen
FeedRunner._factsA feed’s answers once past their own TTLEvery tick, inside live_facts(now)
ContextService._factsAny fact nobody is refreshing, plus a five-minute graceEvery tick, in _sweep()
IcsCalendarProvider._cacheThe text of a calendar file no longer configuredWhenever events are read
RateLimiter.budgetsHosts idle for a day, unless one is being restedAt most hourly, riding along with real traffic

Facts with ttl_s <= 0 are exempt, because arithmetic cannot go stale: sunset today is as true in a month as it is now.

Household control

ContextSettings (settings schema v8) has two levels, borrowed from Home Assistant’s exposed-entities model:

  • feeds is the outbound half. Weather and alerts ship on; everything else ships off and the household turns it on.
  • facts is the per-fact half. An id set False is never rendered and never cached, whatever produced it. An id that is absent keeps the fact’s own default, so a fact added in a later version does not silently appear in a household that opted out of its neighbours.

A feed turned off drops its facts immediately rather than waiting for them to expire, because a household that revokes something expects it gone from the next reply.

What this filled in

awareness/situation.py has declared Environment.outdoor_temp_f and Environment.sun_up since its first version with nothing populating them. Both now come from this layer, which is what turns “it is dark” into “it is dark even though it is daytime, so the shades must be closed”.

Status

Integrated, on the bench Pi against the live services (2026-09-01). One bench.context poll returned real conditions, a real “rain should start around 3 AM” derived from the live hourly probabilities, and an empty-but-successful answer from the alerts feed, for two requests total. Two bugs came out of that run and neither was reachable from a test: the sun was computed for the previous day all morning, and sunrise was being said in UTC because the conversion only ran for a timezone-aware wall clock.

live: the computed provider, the four feeds, the limiter, the registry mechanism, the block renderer, the provider seam, the local calendar, and the weather skill reading from cache.

live also includes the first real provider through the seam: calendar.py reads .ics files from the robot’s own disk. It handles plain, all-day and repeating events (daily, weekly, monthly, yearly, with INTERVAL, BYDAY, COUNT and UNTIL), RFC 5545 line folding, escaped text, and both UTC and floating local times. It does not handle EXDATE, RECURRENCE-ID overrides or BYSETPOS, and an event whose rule it cannot read is skipped rather than approximated: a robot that announces a meeting on the wrong day is worse than one that stayed quiet. Files are cached by mtime, so a large export is parsed when it changes and not every tick.

planned: every non-live row in registry.CATALOG.
