The family web app

The family web surface is a React SPA in web/, served by the robot’s own api app. It replaces the inline panel page whenever a build is present; the panel remains the zero-tooling fallback.

Stack, and the one deviation

  • React 19 + Vite + TypeScript, packages via bun with a lockfile.
  • HeroUI v3 for every interactive component, themed in web/src/index.css (brand accent at hue 288, system font stack).
  • No state library: React context for auth, plain fetch against the api.

The org standard points web frontends at the shared component catalog in the home repo. This repo deviates on purpose (recorded here per STACK.md): the robot site is built from prebuilt HeroUI components only, never hand-rolled ones, so every control is accessible, consistent, and nobody maintains a widget. The CLAUDE.md rule “prebuilt components only” is the enforcement half of this decision.

How it is served

Same-origin is load-bearing: the auth gate uses a cookie session with double-submit CSRF, and the events socket checks Origin against Host, so the site must come from the robot itself, never a separate host.

  • create_app(..., web_dir=...) mounts web/dist when it holds an index.html: hashed assets under /assets, real files by path, and an SPA fallback that serves index.html for client routes (robot/robot/api/site.py).
  • Unknown /api/* paths still 404 as JSON; the catch-all never shadows the API.
  • A built web/dist in the checkout is served automatically (building it is the opt-in); MAIPAI_WEB_DIR points at a build elsewhere, and with no build the panel serves. Until the SPA carries every panel surface (my data, proposals, people, Wi-Fi, persona, backup, the walkthrough), a machine that needs those keeps the panel by not building web/dist; the parity checklist is a repo issue. MAIPAI_WEB_PORT (0 = off) turns the whole web surface on; the shipped systemd unit sets 8080.

Pages

  • Home: status card (/api/state), privacy chips (recording and soft-mute heartbeats), selftest attention items. The battery renders only when pack_known is true; an unmeasured pack draws nothing (the honesty rule).
  • Chat: POST /api/converse, with live sentence streaming assembled from brain/say frames on WS /api/events when the session holds the microphone capability; without it the posted reply renders whole.
  • Call: telepresence signaling state (/api/call), answer/decline/hangup. Live audio and video are not wired yet and the page says so.
  • Settings: rendered entirely from GET /api/settings/schema, so the page cannot drift from the model. Essentials show by default; the Advanced switch reveals the rest. Unavailable settings render dimmed with the schema’s own plain-language reason.

Dev loop

A simulator run prints the one-time pairing code to the terminal (it has no screen to show it on), and waives the knob press: a simulated knob cannot witness a real person, so claiming takes the same audited no-witness path as a body with no knob fitted. A built web/dist is picked up automatically; run cd web && bun run dev instead for hot reload (the Vite proxy forwards /api, including the websocket).

scripts/check.sh lints, typechecks, and builds the site when bun is installed. web/dist is never committed; deploys build it.

Next increments

Voice in the browser lands in this order, mirroring the hub’s proven protocol shapes (WS mic streaming to server-side end-of-turn detection, NDJSON TTS chunks scheduled in WebAudio, ort-web wake models): spoken replies first, then push-to-talk, then the wake word on the Call page. Tracked in the repo issues.
