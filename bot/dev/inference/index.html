Running the model

The robot’s model runs on this machine and nothing about it is fetched at run time. This page is how it is served, which knobs actually move on a Raspberry Pi 5, and the measurements behind each one - because most of them were surprising and two of them reversed a decision.

Every number here was measured on the bench Pi with python -m robot.bench.latency, which refuses to run on a busy machine and refuses to report if the robot spoke during the run. See the design record for why those guards exist.

Serve with llama-server, not Ollama

Ollama is convenient and it costs about 2x here. The same model, same machine, same prompt: 8.76 s through ollama serve, 4.40 s on llama-server directly. It also hides the flags that turn out to matter most, and it decides its own quantization, which is not something a benchmark should let it do.

Ollama ships the binary, so nothing needs building:

Its model store is drwx------ ollama ollama, so the GGUF files live in a directory the robot’s own user owns, downloaded once and pinned by name.

The flags

--threads 4, pinned with taskset -c 0-3. The Pi 5 has four physical cores and no SMT. More threads is cache thrashing, not speed, and pinning stops the scheduler moving the work while the robot’s vision pipeline is also asking for cores.

--batch-size 256 --ubatch-size 64. Desktop guides recommend far larger. This board is memory-bandwidth-bound and bigger batches spend bandwidth it does not have.

--mlock --no-mmap. Pins the weights in RAM. On a 16 GB board a 770 MB model can simply live there, and a page fault mid-inference is a stall a person hears.

-np 1. One sequence slot, which is right for one robot - but be aware of what it means: any second client QUEUES BEHIND A WHOLE REPLY. This is not a theoretical concern. It invalidated three separate benchmark runs before it was understood, because the robot answering a question in the next room made every measurement wait for it.

Q4_K_M is the quantization to use. Q8_0 is unnecessarily heavy for CPU inference at this scale and below Q4 costs real quality for little speed.

--flash-attn is deliberately absent. Its benefit is established on GPUs and mixed on CPU ARM. It is a lever to measure, not to assume.

Gemma 3 needs two more flags, and they are the difference between usable and not

Gemma 3 interleaves sliding-window attention, and without these the server cannot reuse a partial prefix: change one byte of the prompt and it re-reads every token. That produces a very distinctive signature - fast when the prompt repeats exactly, catastrophic when anything changes:

gemma3:1bbyte-identical promptclock line changednew topic
without the flags1.79 s4.40 s12.32 s
with the flags1.61 s2.73 s4.30 s

The robot’s prompt ends with a clock line that turns over every minute, so it lives permanently in the middle column. Without these flags Gemma 3 was written off as unsuited to this robot. With them it is the fastest honest option available.

--swa-full trades a compact window cache for a full-size one. On a 1B model that is a small amount of RAM for a 3x change in the number a person feels.

What the flags did NOT fix, and what actually costs the time

Prompt evaluation dominates. The model re-reads the prompt on any turn where the cached prefix does not match, and it reads at 41-58 tokens a second depending on the model. That arithmetic is the whole latency story:

conditionwhat it meanscost
repeatbyte-identical promptcache hit, under a second
minuteonly the clock line changedmost real turns
freshnew memory, situation and clocka new topic

Because the volatile block sits at the END of the prompt, everything before it should cache - and does, once the server can reuse a partial prefix. That is exactly what the Gemma flags restore.

Turn off thinking, everywhere

Qwen3 and its relatives emit a chain-of-thought block before the answer by default. On a voice robot that is not a latency problem, it is a correctness one: the reply goes to a speaker, so the robot recites its reasoning to the room, one streamed sentence at a time.

and the native route also sends "think": false. Models without a thinking mode ignore both. tests/test_prompt_budget.py counts request bodies against the flag so a fourth one cannot ship without it.

Keep the weights resident

An idle model is unloaded after five minutes by default, and the next question pays a 13-18 second cold load. keep_alive is silently ignored on /v1/chat/completions; Ollama honours it only on its native routes, so cognition/llm/local.py pins the model with an empty /api/generate call on every health probe. Measured: expiry goes from four minutes to fifty-nine.

The board itself

  • Boot from the SSD, not an SD card. Load time and I/O stalls, not steady-state speed.
  • Active cooling is not optional. Sustained inference will reach the soft temperature limit; vcgencmd get_throttled returning anything but 0x0 means some of your measurements were taken on a throttled CPU. Bit 19 means it has happened since boot.
  • The governor is ondemand by default. Worth setting to performance, though on this board it was already sitting at the 2400 MHz maximum, so it did not explain the variance it was suspected of.
  • Do not quantize the KV cache (--cache-type-k/v q8_0) for Gemma 3. It interacts badly with sliding-window attention. It is safe for full-attention models like Llama 3.2 and Qwen3.

The serving stack changes the ANSWERS, not just the speed

This was the genuine surprise. The same model and the same prompt, scored on the 105-question honesty bench:

gemma3:1b, diet prompttraps (81)recall (24)
through Ollama3413
on llama-server, SWA flags4816

A serving change worth 14 traps and 3 recalls. The most likely explanation is that a model which cannot reuse its prefix, running under --context-shift, is not always seeing the prompt anyone thinks it is seeing.

The practical consequence: a model evaluation is only valid for the stack it was run on. An earlier conclusion here - that the prompt diet cost truthfulness - was measured through Ollama, and does not reproduce on llama-server. Numbers do not travel between serving stacks, and neither do the decisions built on them.

Send real chat turns, not a transcript

The robot used to hand the model its whole conversation glued into ONE user message with User: / You: markers - a leftover from completion-style models. Every modern chat template expects turns, and the difference is not cosmetic. Same model, same words, only the packaging:

llama3.2:1btraps (81)recall (24)
transcript in one user message247
real user/assistant turns3517

Recall went from 7 out of 24 to 17: the robot was failing questions it had already been told the answers to, purely because of how the history was packed.

qwen3:0.6b could not be evaluated in the old shape at all - it echoed the previous assistant line back before every answer, on all 105 questions, because a transcript asks a model to continue a document rather than take a turn. That looked exactly like a useless model and was a broken harness.

build_chat_messages is the only shape now; the transcript builder is deleted rather than kept as a fallback.

Turn off thinking, everywhere

Qwen3 and its relatives emit a chain-of-thought block before the answer by default. On a voice robot that is not a latency problem, it is a CORRECTNESS one: the reply goes to a speaker, so the robot recites its reasoning to the room, one streamed sentence at a time.

Every request body that can carry a reply sends "chat_template_kwargs": {"enable_thinking": false}, and the native route also sends "think": false. tests/test_prompt_budget.py counts request bodies against the flag so a fourth cannot ship without it.

Where it ended up

All on llama-server, matched Q4_K_M, real chat turns, two honesty runs each (210 questions per model). minute is the realistic latency case - only the clock line changed:

modellatencytraps (81)recall (24)
qwen3:0.6b1.05 s44, 5317, 15
gemma3:1b + SWA2.73 s48, 4619, 21
llama3.2:1b3.63 s35, 3417, 19

qwen3:0.6b ships. It is a tie with Gemma on honesty across 210 questions and two and a half times faster, on half the parameters. The owner’s call, and the right one: when honesty is that close, take 1.05 s over 2.73 s.

llama3.2:1b - what the robot ran for months - is last on both axes.

Gemma stays a live option rather than a rejected one: with --swa-full --cache-reuse 256 it is fast enough, and if the honesty bar ever rises it is the model to re-test first.

The model on the HAT, inside the robot (2026-09-03)

The conversation model now runs on the AI HAT+ 2 (Hailo-10H), in the robot’s own process, through robot/cognition/llm/hailo.py. Measured beside the live vision pipeline: Qwen3-1.7B reads the prompt at about 110 tokens a second, generates at 4.8, gives a first token in 0.6 s when the runtime keeps the conversation and 2.5 s when it re-reads the whole prompt, and scores 95% on the honesty bench after the guards. The CPU is free for speech throughout. The llama-server path above stays as the fallback and the bench stack.

Choosing it. llm_backend (env MAIPAI_LLM_BACKEND) is auto by default: the HAT when hef/llm.hef is under the models root and the Hailo runtime imports, else llama-server, else the deterministic floor. hailo and server force one; off disables conversation. MAIPAI_LLM_HEF overrides the file. The HEF is the talk-qwen3-1.7b pack (python -m robot.packs.install), pinned by sha256; it needs HailoRT 5.3.0, which the design record installs by hand until Raspberry Pi OS ships it.

How it runs. One worker thread drives hailo_platform.genai.LLM; the HAT holds one sequence, so jobs are serialised, and nothing HailoRT does ever runs on the event loop. The device is opened in the SHARED group on the adapter’s own VDevice (the vision driver opens SHARED too), so the two share the scheduler and the model survives the camera stopping. Every reply has a first-token budget and a whole-reply budget; a breach abandons the job, marks the model down (the health tick reports model_down, the skill floor keeps answering) and the next refresh brings a fresh engine up. The log says when a device stays wedged and needs systemctl restart maipai-bot.service: two test processes proved that a misbehaving client can stall vision until the service restarts, which is why the model is in-process and nothing else may share the HAT.

Keeping the context. The runtime holds the conversation between calls. The chat skill asks the model whether it keeps_context; when it does, build_chat_messages(volatile_on_turn=True) leaves the system block stable (persona, rules, examples) and puts memory, briefing, situation and the clock line in a system-role message just before the user turn. The adapter compares the history it is handed with what the runtime already read; when they match it sends only the tail, otherwise it clears and re-reads. A clipped reply, a trimmed history or a new conversation all re-read, which is the honest thing: the runtime must never believe it said what the room did not hear. The prompt is rendered as ChatML by hand, because a one-message structured prompt would have the model’s template insert its own default system line.

One model per HAT. The runtime holds a single KV cache: a second process loading a language model while the robot holds one fails with “KV-Cache is already in use by another model” (measured 2026-09-03). That is the other reason the model is in-process, and it means the bench (bench.chat --hailo <hef>, the same adapter) runs with the robot stopped: sudo systemctl stop maipai-bot.service first, start after.

The job, not the model: the narrowed chat turn (2026-09-03)

The table above scores the model against a prompt that asked it to know, judge, hold a persona and phrase at once. Three of those left the prompt (see the design record): the household rule rides on the turn the classifier marks, a named thing is looked up before the model sees it, and deterministic guards catch the shapes of lie the bench sorted. python -m robot.bench.honesty now prints a raw column (the model) and a guarded column (what the robot says), and --json keeps every reply so a guard change can be re-scored offline without a model run.

Same 105 questions, all on the bench Pi with the robot running:

On the HAT beside the live vision pipeline, the 1.5B reads a 326-token prompt in 1.5 s (about 220 tokens a second) and generates at 6.8 tokens a second; Qwen3-1.7B reads at about 110 tokens a second, generates at 4.8, and gives a first token in 0.62 s when the runtime keeps the conversation context. The 1.7B on the CPU reads at 27-40 tokens a second and cannot answer in under 3.5 s. Qwen3-1.7B needs HailoRT 5.3.0, which Raspberry Pi OS does not ship; the design record has the by-hand install. A crashing LLM process on the shared HAT took the vision pipeline down with it once, so whatever runs the model is supervised like a driver.

What is actually running

Ollama is removed - binary, install and blobs, about 5 GB. The engine was lifted out of its bundle first, because Ollama ships llama.cpp unmodified and only 22 MB of that 2.1 GB install can run on a Pi at all; the rest is CUDA.

One trap worth repeating for anyone doing that: copy the .so SYMLINKS as well as the files. A find -type f skips them, the binary exits 127 on every start, and the robot loses its model with no obvious cause.
