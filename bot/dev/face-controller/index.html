Face controller

The face controller is a Raspberry Pi Pico 2 (RP2350) that owns both eye panels and the WS2812B mouth. It renders the face locally at 60 fps and takes high-level commands from the Pi over USB serial: a pose name, a gaze offset, a blink, a speech level. The firmware is in firmware/face/, the host client is robot/hal/drivers/face_pico.py, and python -m robot.bench.face drives it.

It is flashed once at build time, speaks only over the local USB cable, has no wireless of any kind, and fetches nothing. Same shape as the HEART knob.

Why it exists

Both 240x320 ST7789 panels on the Pi 5 share SPI0, one chip select each. That means the two eyes take turns on one bus, and the wiring will not carry a fast clock. Measured on the head bench on 2026-08-31:

WhatResult
Whole frames at 24 MHzrender 7.6 ms, push 126.1 ms for the pair, 7.5 fps
Changed-box pushes at 24 MHzrender 2.2 ms, push 47.4 ms, 20.2 fps
8, 16 and 24 MHz through breadboard jumpersall draw correctly
40 MHz through breadboard jumpersdraws nothing at all
SPI chunk size, 4 kB through 150 kBno difference: the link is saturated

Bounding the lit part of each frame and pushing only that box (unioned with the previous box, so a shrinking eye erases behind itself) got 7.5 fps to 20.2 fps, a 2.7x gain for 37% of the bytes. That was the last easy win. A blink is still visibly choppy at 20 fps, and everything else on the Pi competes for the same bus and the same core.

The Pico 2 changes three things at once:

  • Two hardware SPI blocks. One panel each, so the two transfers overlap instead of queueing. The Pi has one bus for both.
  • Short traces. The panels sit next to the microcontroller, so the clock can run at 62.5 MHz, which is the ST7789’s own write-cycle ceiling (16 ns), rather than the 16 MHz the Pi’s jumper harness tolerates.
  • PIO. WS2812B timing on the RP2350’s PIO is a solved problem. On the Pi 5 the same job goes through the RP1’s PIO, which has never been confirmed working for these panels.

At 62.5 MHz on two blocks in parallel, a whole 153.6 kB frame per eye is about 20 ms of wire time and a changed box is closer to 7 ms. 60 fps has room, and the Pi stops spending a core and a bus on pixels. The firmware measures its own frame rate and reports it: python -m robot.bench.face bench prints it, and it has not been measured on real hardware yet.

Wiring

Panel VCC goes to the Pico’s 3V3(OUT) (header pin 36) and BLK to 3V3 as well: “eye off” is black pixels, not a backlight pin, the same as on the Pi-driven panels. Header pins 18 and 23 are grounds inside the two signal groups, so each panel gets a ground return next to its own wires.

SignalRight eye (SPI1)Left eye (SPI0)
SCKGP10, pin 14GP18, pin 24
MOSI (panel SDA/DIN)GP11, pin 15GP19, pin 25
DCGP12, pin 16GP16, pin 21
CSGP13, pin 17GP17, pin 22
RSTGP14, pin 19GP20, pin 26

The mouth’s data line is GP15 (pin 20) into a 74AHCT125 level shifter powered from 5 V; the shifter’s output goes to the matrix DIN. The matrix takes its 5 V from the peripheral buck, never from the Pico: 128 pixels at full white draw about 7.7 A.

The Pico itself connects to the Pi by USB, on the 4-port hub with the other serial peripherals. It draws its own logic power from that cable.

Every pin is in one block at the top of firmware/face/src/config.h. When the face controller is fitted, the Pi’s eye pins (GPIO 6, 7, 8, 10, 11, 25) and mouth pin (GPIO 19) go free; the hardware record keeps both allocations, because the Pi-driven path still works and is what the current bench uses.

Clocks

EYE_SPI_HZ defaults to 62,500,000. SYS_CLOCK_KHZ is 125,000, not the RP2350’s stock 150,000, because the SPI divider only produces clk_peri divided by an even prescale: 125 MHz gives exactly 62.5 MHz, while 150 MHz gives 75 MHz (over the panel’s spec) or 37.5 MHz and nothing between.

If a panel draws garbage or nothing, halve EYE_SPI_HZ to 31250000, then 15625000. The status command reports the baud rate the SPI block actually settled on, so what is running is never a guess.

How the face is drawn

The renderer is a port of robot/hal/drivers/eye_renderer.py, not a lookalike: same rounded-pill signed distance field, same amber (255, 150, 30), same halo falloff and the same reach cutoff where the glow packs to black in RGB565, same squint and curve cuts, same tilted lids with the inner corner mirrored per eye, same asym on the right eye, same blink phase, gaze and jitter, same RGB565 packing. The pose table in firmware/face/src/poses.c carries all seventeen poses field for field from robot/face/poses.py.

Rendering both renderers over 102 cases (every pose, both eyes, three blink and gaze combinations) gave identical boxes in every case and identical pixels in 100 of them; two cases differed by one step in one 5-bit channel on 2 pixels out of 36,337, which is float rounding at a truncation boundary.

Only the box the eye can light is rendered and pushed, unioned with the box the previous frame lit, exactly as the Python driver does. Nothing holds a whole framebuffer: each eye renders 16 rows at a time into one of two small buffers while the other is on the wire, so the four buffers together are 31 kB out of the RP2350’s 520 kB.

Core 0 renders the left eye, reads the serial link and drives the mouth. Core 1 renders the right eye. Each core owns its own SPI block and DMA channel. FACE_USE_CORE1 set to 0 puts both eyes on core 0, which is slower but takes the second core out of the picture while bringing a board up.

The firmware also owns the idle behaviour: blinks on exponentially distributed intervals scaled by the pose’s blink_scale and by arousal, and ballistic micro-saccades. The host sets a pose once and the face stays alive without another byte crossing the wire.

The mouth

Two chained 8x8 WS2812B panels, 16 wide by 8 tall, driven from PIO at 800 kHz by DMA so the 3.8 ms transfer never stalls the eye loop. The pattern is the same centre-out speech shape as robot/hal/drivers/mouth_renderer.py: width and height grow with the level, columns nearer the centre are brighter, and valence bends the outer columns up or down.

The brightness cap is enforced in the firmware, not trusted from the host. It defaults to 25 percent and anything above 40 percent is refused with an err line rather than clamped silently, because 128 pixels at full white draw about 7.7 A. The host client refuses it too, so a mistake gets a Python error before it gets a serial one.

The (x, y) to strip index map is the same MatrixLayout the Python driver uses (panel order, serpentine rows, per-panel 180 degree rotation, row or column major) and is set at run time with the layout command, because the physical pixel order of the panels is not known until they are on the bench.

The protocol

One command per line terminated by \n, one reply per command starting with ok or err . Plain text on purpose: the commands the Pi sends are the ones a person types into a terminal. It is defined in firmware/face/src/protocol.h, mirrored by the encoders in robot/hal/drivers/face_pico.py, and PROTO_VERSION is bumped on both sides together.

CommandReply
helpthe command list
versionok version maipai-face 0.1.0 rp2350 proto 1
statusfps, frames, pose, gaze, brightness, SPI clock, last frame time and bytes
posesthe seventeen pose names
pingok pong
pose <name>ok pose happy
gaze <dx> <dy>each -1..1, 0 0 straight ahead
blink [double]ok blink single
speak <level> [valence]level 0..1, valence -1..1
bright eyes <0..1>eye glow multiplier
bright mouth <0..0.40>above the ceiling is refused
idle <on|off>auto blinks and micro-saccades
layout <order> <serp> <rot1> <rot2> <rowmajor>mouth pixel mapping
blank / wakeeyes and mouth black, and back

Failures name what was wrong: err unknown-command <word>, err unknown-pose <name>, err usage <cmd> <what it wants>, err range <field> <what is allowed>, err too-long. An unknown command is never answered with silence.

Build and flash

Needs CMake 3.13 or newer, arm-none-eabi-gcc, and Python 3. The Pico SDK is downloaded, never vendored: set PICO_SDK_PATH if you have a checkout, otherwise CMake clones the pinned tag into the build directory the first time.

Then unplug the Pico, hold BOOTSEL, plug it back in, release BOOTSEL, and drag build/maipai_face.uf2 onto the RP2350 drive that appears. The board reboots running the firmware and enumerates as a USB serial device named “MaiPai face controller”.

Driving it from the Pi

robot.bench.head check lists the face controller as an optional device: it is reported either way and never makes the head look broken, because the Pi can still drive the panels directly and that is what the current bench does.

Not wired into the running robot yet. robot.face.renderer pushes pixels to an EyePair, and the face controller takes expressions instead, so open_head_devices still opens the Pi’s own TwoEyes. Swapping the renderer over to FacePico.show_expression when a board is attached is the next step, and it wants a board on the bench to prove it.

What has not been proved yet

Everything above the protocol line is measured; everything below it is arithmetic waiting for a board. The 60 fps target, the 62.5 MHz clock actually holding on real wiring, the two DMA transfers really overlapping, the WS2812B timing, and the per-pixel render cost on a 125 MHz Cortex-M33 have not been run on hardware. python -m robot.bench.face bench prints what the firmware measures, and those numbers belong in the hardware record once there is a board to take them from.
